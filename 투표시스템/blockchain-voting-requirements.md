# 1. PRD — 제품 요구사항 문서

## 1.1 제품 개요

이더리움 세폴리아(Sepolia) 테스트넷을 기반으로 동작하는 웹 투표 시스템이다.
투표의 핵심 로직(등록, 투표, 집계)은 스마트 컨트랙트로 처리하여 위·변조를 방지하고,
후보자 사진 등 비핵심 데이터는 중앙 서버에서 관리한다.
Chrome 브라우저와 MetaMask 지갑을 통해 접근하며, 수업 실습 목적으로 소규모 환경(동접 최대 5명, 투표 수 30개 미만)을 가정한다.

## 1.2 배경 및 목적

| 항목 | 내용 |
|------|------|
| 목적 | 블록체인 기반 투표 시스템의 구조와 동작 원리를 실습으로 이해 |
| 대상 네트워크 | Ethereum Sepolia Testnet |
| 사용 환경 | Chrome 브라우저 + MetaMask 확장 프로그램 |
| 운영 규모 | 동시 접속 최대 5명, 총 투표 수 30개 미만 |

## 1.3 사용자 유형

### 관리자 (Admin)
- 스마트 컨트랙트를 배포한 지갑 주소 소유자
- 후보자 등록·삭제, 선거 시작·종료 권한 보유
- 일반 사용자 기능(투표)도 동일하게 사용 가능

### 일반 사용자 (Voter)
- 세폴리아 네트워크에 연결된 MetaMask 지갑 보유자
- 진행 중인 선거에서 1인 1표 행사 가능
- 실시간 득표 현황 열람 가능

## 1.4 핵심 기능 요구사항

### F-01 MetaMask 지갑 연결
- 사용자는 MetaMask로 세폴리아 네트워크에 연결하여 서비스에 접근한다.
- 지갑 미연결 상태에서는 투표 및 관리 기능을 사용할 수 없다.
- 연결된 지갑 주소와 세폴리아 네트워크 여부를 화면에 표시한다.

### F-02 후보자 관리 (관리자 전용)
- 후보자 이름과 사진을 등록할 수 있다.
- 사진은 서버에 업로드되고, 이름은 스마트 컨트랙트에 저장된다.
- 후보자 등록은 선거 시작 전에만 가능하다.
- 등록된 후보자를 삭제할 수 있다 (선거 시작 전에만).

### F-03 선거 관리 (관리자 전용)
- 관리자는 선거를 시작할 수 있다. 후보자가 2명 미만이면 시작 불가.
- 관리자는 진행 중인 선거를 종료할 수 있다.
- 한 번에 하나의 선거만 운영된다.
- 선거는 준비 중 → 진행 중 → 종료의 단방향 상태로 전환된다.

### F-04 투표
- 진행 중인 선거에서 후보자 1명을 선택하여 투표한다.
- MetaMask 서명을 통해 트랜잭션을 블록체인에 기록한다.
- 동일 지갑 주소는 1회만 투표 가능하며, 중복 투표 시 컨트랙트에서 거부된다.
- 투표가 종료된 선거에는 투표할 수 없다.

### F-05 투표 현황 열람
- 선거 진행 중: 후보자별 실시간 득표 수를 공개한다.
- 선거 종료 후: 최종 득표 수와 당선자(최다 득표자)를 표시한다. 동점 시 해당 후보 전원을 공동 당선자로 표시한다.
- 선거 준비 중: 등록된 후보자 목록만 표시한다.

## 1.5 비기능 요구사항

| 항목 | 요구사항 |
|------|----------|
| 네트워크 | Ethereum Sepolia Testnet 전용 |
| 브라우저 | Chrome (MetaMask 확장 프로그램 설치 필요) |
| 규모 | 동접 최대 5명, 투표 수 30개 미만 |
| 가용성 | 수업 시간 내 정상 동작 (SLA 미적용) |
| 보안 | 중복 투표 방지는 스마트 컨트랙트 레벨에서 처리 |
| 투명성 | 투표 진행 중 실시간 득표 수 공개 (공개 투표) |

## 1.6 제약 사항

- 세폴리아 네트워크 가스비(테스트 ETH)는 사용자가 직접 보유해야 함 (무료 faucet 이용 가능: Google Cloud Faucet, Stakely Faucet 권장)
- **Sepolia 테스트넷은 2026년 9월 30일 EOL(서비스 종료) 예정** — 해당 일자 이전에 실습을 완료해야 함
- 스마트 컨트랙트 배포 후 동일 선거 세션 내에서만 운영 (재배포 시 데이터 초기화)
- 사진 파일은 서버 로컬 저장소에 보관 (클라우드 스토리지 미사용)
- 투표 결과 취소·수정 불가 (블록체인 특성상 불변)
- 관리자 인증은 프론트엔드의 UI 편의 기능이며, 실제 권한 강제는 컨트랙트의 `onlyOwner` modifier가 담당함 (프론트엔드 우회 시도 시 컨트랙트가 자동 거부)

# 2. SRS — 소프트웨어 요구사항 명세

## 2.1 시스템 구성

```
[Chrome Browser]
      │
      ├── MetaMask (BrowserProvider)
      │         │  트랜잭션 서명
      │         ▼
      │   [Sepolia HTTP RPC]          [Alchemy/Infura WSS RPC]
      │         │                              │
      │         ▼                              ▼
      │   [Smart Contract]  ←── 이벤트 구독 ──[WebSocketProvider]
      │   (투표 핵심 로직)         (VoteCast 등)
      │
      └── HTTP 요청
                │
                ▼
         [Backend Server]   ← 후보자 사진/메타데이터
                │
                ▼
           [Database]       ← 후보자 보조 정보 저장
```

> BrowserProvider(MetaMask)는 트랜잭션 서명 전용, WebSocketProvider(Alchemy/Infura WSS)는 컨트랙트 이벤트 구독 전용으로 역할을 분리한다.

## 2.2 기술 스택 (권고)

실습 규모에 맞춰 설정·운영이 단순한 스택을 권고한다.

| 레이어 | 기술 | 비고 |
|--------|------|------|
| 스마트 컨트랙트 | Solidity | Remix IDE 또는 Hardhat으로 배포 |
| 프론트엔드 | React + Vite | Ethers.js v6으로 컨트랙트 연동 |
| 백엔드 | Node.js + Express | 사진 업로드·메타데이터 관리 |
| 데이터베이스 | SQLite (better-sqlite3) | 설치 불필요, 파일 기반 DB |
| 파일 저장 | 서버 로컬 파일시스템 | 30명 미만이므로 클라우드 불필요 |
| 네트워크 | Ethereum Sepolia Testnet | Alchemy 또는 Infura RPC 사용 (**2026.09.30 EOL 예정**) |

## 2.3 스마트 컨트랙트 명세

### 2.3.1 상태 변수

| 변수명 | 타입 | 설명 |
|--------|------|------|
| `owner` | `address` | 컨트랙트 배포자 주소 (관리자) |
| `electionStatus` | `enum` | `READY` / `ACTIVE` / `ENDED` |
| `candidates` | `Candidate[]` | 후보자 배열 |
| `candidateCounter` | `uint` | 후보자 ID 자동 증가 카운터 (삭제 후에도 재사용하지 않음) |
| `hasVoted` | `mapping(address ⇒ bool)` | 투표 여부 매핑 |
| `totalVotes` | `uint` | 총 투표 수 (vote() 호출 시마다 1 증가) |

### 2.3.2 데이터 구조

```
Candidate {
  uint    id          // 후보자 고유 ID (candidateCounter 기반 auto-increment; 배열 인덱스와 분리)
  string  name        // 후보자 이름
  uint    voteCount   // 득표 수
}
```

> **구현 주의**: `removeCandidate` 구현 시 Solidity `delete array[i]`는 원소를 기본값으로 초기화할 뿐 배열 길이를 줄이지 않아 gap이 발생한다. 본 명세에서는 **swap-and-pop 패턴**을 채택한다 — 삭제 대상 원소를 배열의 마지막 원소로 덮어쓴 뒤 `pop()`으로 마지막 원소를 제거한다. 이로 인해 배열 순서는 바뀔 수 있으나, ID는 각 원소의 `id` 필드로 식별하므로 무관하다.

### 2.3.3 함수 명세

| 함수 | 접근 권한 | 설명 | 전제 조건 |
|------|-----------|------|-----------|
| `addCandidate(string name)` | 관리자 | 후보자 이름을 컨트랙트에 등록; `candidateCounter`를 1 증가시켜 ID 부여 | 선거 상태 = READY |
| `removeCandidate(uint id)` | 관리자 | 후보자 삭제; swap-and-pop 패턴으로 배열 gap 없이 제거 | 선거 상태 = READY |
| `startVoting()` | 관리자 | 선거 시작; `candidates` 배열 길이(활성 후보 수)가 2 이상인지 확인 | 후보자 수 ≥ 2, 상태 = READY |
| `endVoting()` | 관리자 | 선거 종료 | 상태 = ACTIVE |
| `vote(uint candidateId)` | 모든 지갑 | 해당 후보자에게 투표 | 상태 = ACTIVE, 미투표자 |
| `getCandidates()` | 누구나 (view) | 후보자 전체 목록 반환 (view 함수이므로 가스비 없음) | — |
| `getElectionStatus()` | 누구나 (view) | 현재 선거 상태 반환 | — |
| `checkHasVoted(address)` | 누구나 (view) | 특정 주소의 투표 여부 확인 | — |
| `getWinner()` | 누구나 (view) | 최다 득표 후보자 ID 목록 반환; **동점 시 해당 ID 전체를 배열로 반환** | 상태 = ENDED |

### 2.3.4 이벤트

| 이벤트 | 발생 시점 | 파라미터 |
|--------|-----------|----------|
| `CandidateAdded` | 후보자 등록 시 | `id`, `name` |
| `CandidateRemoved` | 후보자 삭제 시 | `id` |
| `VotingStarted` | 선거 시작 시 | — |
| `VotingEnded` | 선거 종료 시 | — |
| `VoteCast` | 투표 완료 시 | `voter(address)`, `candidateId` |

### 2.3.5 오류 처리 (revert 조건)

| 조건 | 오류 메시지 |
|------|------------|
| 관리자 전용 함수를 일반 사용자가 호출 | `"Only owner"` |
| 선거 시작 후 후보자 등록 또는 삭제 시도 | `"Voting already started"` |
| 후보자 2명 미만인 상태에서 선거 시작 | `"Need at least 2 candidates"` |
| READY 또는 ENDED 상태에서 `endVoting()` 호출 | `"Voting is not active"` |
| 이미 투표한 주소가 재투표 시도 | `"Already voted"` |
| ACTIVE 상태가 아닐 때 `vote()` 호출 | `"Voting is not active"` |
| 존재하지 않는 후보자 ID로 투표 시도 | `"Invalid candidate"` |
| ENDED 상태가 아닐 때 `getWinner()` 호출 | `"Voting not ended"` |

## 2.4 백엔드 API 명세

후보자 사진 및 보조 메타데이터를 관리하는 REST API.

> **등록 순서 원칙**: 후보자 등록 시 컨트랙트 호출(`addCandidate`)을 먼저 수행하여 `contractId`를 확보한 뒤, 해당 ID로 사진을 서버에 업로드한다. 이를 통해 `contractId`가 항상 알려진 상태에서 API를 호출할 수 있다.

### 엔드포인트 목록

#### `POST /api/candidates`
- 후보자 보조 정보 등록 (사진 업로드 포함)
- **컨트랙트 트랜잭션 확인 후 호출** (contractId가 이미 확정된 상태)
- Request: `multipart/form-data`

| 필드 | 타입 | 필수 | 설명 |
|------|------|------|------|
| `contractId` | number | Y | 스마트 컨트랙트의 후보자 ID (addCandidate 이벤트에서 획득) |
| `name` | string | Y | 후보자 이름 (컨트랙트와 일치) |
| `photo` | file | N | 후보자 사진 (jpg/png, 5MB 이하) |

- Response: `{ id, contractId, name, photoUrl }`

#### `GET /api/candidates`
- 등록된 후보자 보조 정보 전체 조회
- Response: `[{ id, contractId, name, photoUrl }, ...]`

#### `GET /api/candidates/:contractId`
- 특정 후보자 보조 정보 조회
- Response: `{ id, contractId, name, photoUrl }`

#### `DELETE /api/candidates/:contractId`
- 후보자 보조 정보 및 사진 파일 삭제 (파일도 함께 삭제)
- Response: `{ success: true }`

#### `GET /api/health`
- 서버 상태 확인
- Response: `{ status: "ok" }`

### 공통 규칙
- 모든 응답은 `application/json`
- 사진 파일은 서버 `/uploads/` 디렉토리에 저장
- 파일명은 UUID로 변환하여 저장 (원본 파일명 미사용)
- 백엔드 별도 관리자 인증 미적용 (실습 규모 고려); 실제 권한 강제는 컨트랙트의 `onlyOwner`가 담당

## 2.5 데이터 모델

### candidates 테이블 (SQLite)

| 컬럼 | 타입 | 설명 |
|------|------|------|
| `id` | INTEGER PK | 자동 증가 |
| `contract_id` | INTEGER UNIQUE | 스마트 컨트랙트의 후보자 ID |
| `name` | TEXT | 후보자 이름 |
| `photo_filename` | TEXT | 저장된 파일명 (없으면 NULL) |

## 2.6 프론트엔드 기능 요구사항

### 공통 요구사항
- 페이지 로드 시 MetaMask 설치 여부 확인
- MetaMask 연결 시 세폴리아 네트워크(Chain ID: `11155111`, hex: `0xaa36a7`) 여부 검증
- 잘못된 네트워크 연결 시 `wallet_switchEthereumChain` 메서드로 세폴리아 전환 요청
- 네트워크가 MetaMask에 미등록된 경우 `wallet_addEthereumChain`으로 추가 요청
- 트랜잭션 제출 후 처리 중 상태(로딩)를 사용자에게 표시

### Provider 구분 (Ethers.js v6)

Ethers.js v6에서 MetaMask의 `BrowserProvider`는 HTTP 기반으로만 동작하여 이벤트 구독이 불안정하다. 다음과 같이 역할을 분리한다.

| Provider 종류 | 역할 | 비고 |
|---------------|------|------|
| `BrowserProvider` (MetaMask) | 트랜잭션 서명 전용 | `window.ethereum` 기반 |
| `WebSocketProvider` (Alchemy/Infura WSS URL) | 컨트랙트 이벤트 구독 전용 | `wss://` URL 필수, HTTP URL 불가 |

이벤트 구독이 복잡한 경우 `queryFilter` 기반 주기 폴링(5초 간격)을 대안으로 사용할 수 있다.

### 관리자 판별
- 연결된 지갑 주소와 컨트랙트의 `owner()` 반환값을 비교
- 일치하면 관리자 메뉴 노출, 불일치하면 숨김
- **이 비교는 UI 표시 편의용**이며, 실제 권한 강제는 컨트랙트의 `onlyOwner` modifier가 수행 (프론트엔드를 우회하더라도 컨트랙트가 거부)

### 상태별 화면 전환

| 선거 상태 | 표시 내용 |
|-----------|-----------|
| READY | 후보자 목록 (득표 수 미표시), 투표 버튼 비활성화 |
| ACTIVE | 후보자별 실시간 득표 수 + 투표 버튼 활성화 |
| ENDED | 최종 득표 수 + 당선자 강조 표시, 투표 버튼 숨김 |

## Phase 1 — 스마트 컨트랙트 구현 및 배포

**목표**: `Voting.sol` 완성 후 Sepolia 테스트넷에 배포하고 모든 컨트랙트 함수가 정상 동작함을 확인한다.

### 구현 항목

- [ ] `Voting.sol` 작성
  - 상태 변수: `owner`, `electionStatus`, `candidates[]`, `candidateCounter`, `hasVoted`, `totalVotes`
  - `Candidate` 구조체 정의
  - `onlyOwner` modifier
  - 함수 전체 구현: `addCandidate`, `removeCandidate`(swap-and-pop), `startVoting`, `endVoting`, `vote`, `getCandidates`, `getElectionStatus`, `checkHasVoted`, `getWinner`(동점 배열 반환)
  - 이벤트 정의: `CandidateAdded`, `CandidateRemoved`, `VotingStarted`, `VotingEnded`, `VoteCast`
  - `revert` 조건 전체 적용 (SRS 2.3.5 참고)
- [ ] Remix IDE에서 컴파일 (Solidity 버전 명시)
- [ ] Remix "Injected Provider - MetaMask"로 Sepolia 배포
- [ ] 배포된 컨트랙트 주소 및 ABI를 별도 파일(`contract/`)에 저장

### 코드 리뷰 체크리스트

- `removeCandidate`: `delete array[i]` 대신 swap-and-pop 패턴 사용 여부
- `getWinner`: 동점 시 ID를 배열로 반환, `ENDED` 상태 guard 적용 여부
- `vote`: `ACTIVE` 상태 guard + `hasVoted` 중복 투표 방지 + 유효하지 않은 후보 ID 거부 여부
- `startVoting`: 활성 후보 수(배열 길이)가 2 미만이면 revert 여부
- 모든 관리자 전용 함수에 `onlyOwner` modifier 적용 여부
- 이벤트 emit 누락 없는지 확인

### 검증 및 테스트

| 시나리오 | 예상 결과 |
|----------|-----------|
| `addCandidate("홍길동")` × 3 회 호출 | candidates 배열에 id=1,2,3 추가 |
| `removeCandidate(2)` 호출 후 `getCandidates()` | id=1,3 반환 (순서 무관), 배열 길이 2 |
| 후보 1명인 상태에서 `startVoting()` | revert "Need at least 2 candidates" |
| 후보 2명 이상인 상태에서 `startVoting()` | 상태 ACTIVE 전환, `VotingStarted` 이벤트 |
| 동일 주소로 `vote()` 2회 시도 | 두 번째 호출 revert "Already voted" |
| ACTIVE 상태에서 `vote(candidateId)` | `VoteCast` 이벤트, 해당 후보 voteCount 증가 |
| `endVoting()` 후 `getWinner()` | 최다 득표 후보 ID 배열 반환 |
| 동점 상황에서 `getWinner()` | 동점 후보 ID 모두 포함된 배열 반환 |
| Sepolia Etherscan에서 컨트랙트 확인 | 소스코드 및 트랜잭션 히스토리 조회 가능 |

### 사이드 이펙트 검증

- `candidateCounter`가 삭제 후 재사용되지 않음을 확인 (삭제 후 추가 시 이전 최대값+1 부여)
- swap-and-pop 이후 배열에 gap 없음 확인 (`getCandidates()` 반환 배열 길이 == 활성 후보 수)

### 누적 테스트 (Phase 1 전체)

- Remix 콘솔에서 전체 시나리오(후보 등록 → 선거 시작 → 투표 3회 → 선거 종료 → 당선자 확인) 순서대로 실행
- Sepolia Etherscan에서 각 트랜잭션의 이벤트 로그 확인

### 검증 및 테스트

| 시나리오 | 예상 결과 |
|----------|-----------|
| `POST /api/candidates` (사진 포함) | DB 저장, 파일 `/uploads/`에 저장, `photoUrl` 반환 |

| `GET /api/candidates` | 등록된 후보자 전체 목록 반환 |
| `GET /api/candidates/:contractId` | 해당 후보자 단건 반환 |
| `GET /api/candidates/999` (없는 ID) | 404 반환 |
| `DELETE /api/candidates/:contractId` | DB 삭제 + 파일 삭제, `{ success: true }` 반환 |
| `GET /api/health` | `{ status: "ok" }` 반환 |
| 동일 `contractId`로 POST 2회 | 두 번째 요청 오류 반환 (UNIQUE 제약 위반) |

### 사이드 이펙트 검증

- `DELETE` 후 `/uploads/` 디렉토리에 해당 파일이 남아 있지 않음 확인
- 사진 없이 등록한 후보자를 삭제해도 오류 없이 처리되는지 확인

### 누적 테스트 (Phase 1 + 2)

- `DELETE /api/candidates/:contractId` 후 `GET /api/candidates` 응답에서 해당 항목 미포함 확인

## Phase 4 — 홈 화면 (선거 현황 표시)

**목표**: 선거 상태(READY/ACTIVE/ENDED)에 따라 홈 화면이 올바르게 전환되고, 후보자 목록과 득표 수가 정상 표시된다.

### 구현 항목

- [ ] 선거 상태 훅 (`useElectionStatus`): `getElectionStatus()` 폴링 또는 `VotingStarted`/`VotingEnded` 이벤트 구독
- [ ] 후보자 목록 훅 (`useCandidates`): 컨트랙트 `getCandidates()` + 백엔드 `GET /api/candidates` 병합
- [ ] **READY 화면** (S-01 상태 A)
  - 후보자 카드 (사진 + 이름만, 득표 수 미표시)
  - 후보자 0명일 때 "등록된 후보자가 없습니다" 안내
  - "⏳ 선거 준비 중" 상태 배너
- [ ] **ACTIVE 화면** (S-01 상태 B)
  - 후보자별 득표 수 막대 그래프 (전체 대비 비율, 숫자 병기)
  - 총 투표 수 표시
  - "🟢 투표 진행 중" 상태 배너
  - `[투표하기]` 버튼 (비활성화 상태 — Phase 5에서 연결)
  - `VoteCast` 이벤트 수신 시 득표 수 자동 갱신 (WebSocketProvider)
- [ ] **ENDED 화면** (S-01 상태 C)
  - 당선자 강조 박스 (`getWinner()` 기반, 공동 당선 처리)
  - 나머지 후보자 카드 (득표 수 + 비율)
  - Sepolia Etherscan 링크 자동 생성
  - "🏁 투표 종료" 상태 배너
- [ ] 백엔드에서 `photoUrl`이 없는 후보자는 기본 아바타 이미지로 폴백

### 코드 리뷰 체크리스트

- 컨트랙트 데이터(득표 수)와 백엔드 데이터(사진)를 `contractId`로 정확히 매칭하는지 확인
- `getWinner()` 반환 배열 원소가 1개 vs 2개 이상일 때 UI 분기 처리 여부
- 이벤트 구독 해제(`off` 또는 컴포넌트 언마운트 클린업) 여부
- 상태 전환 시 이전 상태 UI 잔존 없이 완전히 교체되는지 확인

### 검증 및 테스트

| 시나리오 | 예상 결과 |
|----------|-----------|
| 상태 READY + 후보자 3명 | 카드 3개, 득표 수 미표시, 투표 버튼 없음 |
| 상태 READY + 후보자 0명 | "등록된 후보자가 없습니다" 안내 |
| 상태 ACTIVE | 막대 그래프 + 투표하기 버튼 표시 |
| 다른 브라우저에서 투표 → 현재 화면 | VoteCast 이벤트 수신 후 득표 수 자동 갱신 |
| 상태 ENDED + 단독 당선 | 당선자 1명 강조 박스 |
| 상태 ENDED + 동점 | "공동 당선자" 표시, 해당 후보 모두 강조 |
| Etherscan 링크 클릭 | 올바른 컨트랙트 주소 URL로 이동 |

### 사이드 이펙트 검증

- 상태가 READY → ACTIVE로 전환될 때(이벤트 수신) 페이지 새로고침 없이 UI 자동 전환 확인
- 사진 없는 후보자 카드에서 기본 아바타 표시, 레이아웃 깨짐 없음 확인

### 누적 테스트 (Phase 1 + 2 + 3 + 4)

- Phase 1 컨트랙트에 후보자 3명 등록, Phase 2 백엔드에 사진 업로드 → 홈 화면에 사진 포함 카드 표시 확인
- Phase 1에서 `startVoting()` 실행 → 홈 화면 자동으로 ACTIVE 상태 전환 확인
- Phase 1에서 `vote()` 실행 → 홈 화면 득표 수 즉시 갱신 확인

## Phase 5 — 투표 플로우

**목표**: 투표 버튼 활성화 로직, 투표 확인 모달, MetaMask 트랜잭션 서명, 상태 피드백을 완성한다.

### 구현 항목

- [ ] `checkHasVoted(address)` 조회 훅 — 연결된 지갑 주소 기준
- [ ] `[투표하기]` 버튼 상태 로직
  - 지갑 미연결: 비활성화 + 툴팁 "투표하려면 지갑을 연결하세요"
  - 이미 투표한 지갑: `✓ 투표 완료` 표시, 비활성화
  - ACTIVE + 미투표: 활성화
- [ ] 투표 확인 모달 (S-02)
  - 후보자 사진, 이름, 영구 기록 경고 문구, 내 지갑 주소 표시
  - `[취소]` → 모달 닫힘
  - `[MetaMask로 투표]` → 트랜잭션 서명 팝업 호출
- [ ] 트랜잭션 진행 단계 표시
  - 서명 대기 중: 로딩 스피너, 버튼 비활성화
  - 서명 거부: 오류 메시지 표시, 모달 유지
  - 처리 중(mempool): "처리 중..." 스피너
  - 블록 확인 완료: "투표 완료!" 성공 메시지 → 모달 닫힘
- [ ] 트랜잭션 실패 오류 메시지 사용자 친화적 변환
  - "Already voted" → "이미 투표하셨습니다"
  - 가스비 부족 → "테스트 ETH가 부족합니다"
  - 기타 revert → 원인 메시지 표시

### 코드 리뷰 체크리스트

- `BrowserProvider`로 서명, `WebSocketProvider`로 이벤트 구독이 분리되어 있는지 확인
- `vote()` 호출 시 `candidateId`가 컨트랙트의 `id` 필드 값(배열 인덱스 아님)으로 전달되는지 확인
- 트랜잭션 해시 획득 후 `tx.wait()`로 블록 확인을 기다리는지 확인 (제출만 하고 완료 확인 누락 방지)
- 서명 거부 시 `code === 'ACTION_REJECTED'` 등 에러 코드로 분기하는지 확인

### 검증 및 테스트

| 시나리오 | 예상 결과 |
|----------|-----------|
| 지갑 미연결 상태에서 `[투표하기]` | 버튼 비활성화, 툴팁 표시 |
| ACTIVE 상태 + 미투표 지갑으로 `[투표하기]` 클릭 | 투표 확인 모달 표시 |
| 모달에서 `[취소]` | 모달 닫힘, 홈 화면 복귀 |
| `[MetaMask로 투표]` 클릭 후 MetaMask에서 거부 | 오류 메시지 표시, 모달 유지 |
| `[MetaMask로 투표]` 클릭 후 서명 완료 | "처리 중..." → "투표 완료!" → 모달 닫힘 |
| 투표 완료 후 해당 후보 카드 | `✓ 투표 완료` 표시, 득표 수 +1 반영 |
| 이미 투표한 지갑으로 `vote()` 직접 호출 | 컨트랙트 revert, "이미 투표하셨습니다" 표시 |
| READY/ENDED 상태에서 `[투표하기]` | 버튼 미표시 또는 비활성화 |

### 사이드 이펙트 검증

- 투표 완료 후 홈 화면의 득표 수가 이중으로 갱신(이벤트 + 상태 직접 갱신 중복)되지 않는지 확인
- 트랜잭션 처리 중 다른 버튼 클릭이 차단되는지 확인

### 누적 테스트 (Phase 1 ~ 5)

- 2개 브라우저 창에서 각각 다른 지갑으로 동시에 투표 → 양쪽 화면에서 득표 수 실시간 갱신 확인
- 한 지갑으로 투표 후 동일 지갑으로 재투표 시도 → 컨트랙트 revert, 친화적 메시지 표시 확인
- 전체 투표 플로우(지갑 연결 → 투표 확인 → 서명 → 완료) E2E 시나리오 1회 완주

## Phase 6 — 관리자 패널 + 최종 통합 검증

**목표**: 관리자 전용 기능(후보자 등록·삭제, 선거 시작·종료)을 완성하고 전체 시스템을 E2E로 검증한다.

### 구현 항목

- [ ] 관리자 감지 로직: 연결 지갑 주소 vs 컨트랙트 `owner()` 비교 → `isAdmin` 상태
- [ ] 헤더에 관리자 전용 `[관리자 패널]` 링크 조건부 노출
- [ ] `/admin` 라우트 가드: 비관리자 접근 시 "접근 권한이 없습니다" 메시지 + 홈 리다이렉트
- [ ] 관리자 패널 (S-03)
  - **선거 상태 관리 섹션**
    - 현재 상태 텍스트 표시
    - `[▶ 선거 시작]`: 후보자 2명 미만 시 비활성화 + 안내 문구; ACTIVE/ENDED 시 숨김
    - `[■ 선거 종료]`: ACTIVE 시에만 표시
  - **후보자 관리 섹션**
    - `[+ 후보자 등록]`: READY 상태만 활성화, ACTIVE/ENDED 시 비활성화
    - 후보자 테이블: ID, 이름, 사진 썸네일, `[삭제]` 버튼 (READY 상태만 활성화)
- [ ] 후보자 등록 모달 (S-04)
  - 이름 입력 (필수), 사진 업로드 (선택, 드래그앤드롭 + 파일 선택, 미리보기)
  - 등록 프로세스: 이름 유효성 검사 → `addCandidate()` 컨트랙트 호출 → `CandidateAdded` 이벤트에서 `contractId` 획득 → `POST /api/candidates` (사진 있으면 포함)
  - 각 단계별 로딩 표시 및 오류 처리
- [ ] 후보자 삭제 플로우: `removeCandidate(id)` 컨트랙트 호출 → 완료 후 `DELETE /api/candidates/:contractId` 백엔드 삭제
- [ ] 선거 시작/종료 플로우: 각각 MetaMask 서명 → 트랜잭션 완료 대기 → 상태 갱신

### 코드 리뷰 체크리스트

- 후보자 등록 시 컨트랙트 호출이 백엔드 API 호출보다 반드시 앞서는지 확인 (contractId 확보 순서)
- `CandidateAdded` 이벤트에서 `contractId`를 올바르게 파싱하는지 확인
- 후보자 삭제 시 컨트랙트 삭제 완료 후 백엔드 삭제 호출 순서 확인
- 관리자 권한 체크가 UI 레벨(isAdmin)에서 선행되고, 실제 강제는 컨트랙트 `onlyOwner`가 담당함을 코드 주석 또는 구조로 명확히 표현
- 선거 시작 버튼 비활성화 조건이 "candidates 배열 길이 < 2" 임을 확인 (삭제 후 길이 정확히 반영)

- 후보자 삭제 후 홈 화면 후보자 카드 즉시 사라짐 확인
- 선거 시작 후 관리자 패널의 `[+ 후보자 등록]`과 `[삭제]` 버튼이 비활성화되는지 확인
- 비관리자 지갑이 직접 `addCandidate()` 호출 시 컨트랙트 revert 확인 (프론트엔드 우회 테스트)

### 누적 테스트 — 전체 E2E 시나리오

전체 시스템을 처음부터 끝까지 실행하는 최종 통합 시나리오.

```
1. 관리자 지갑으로 /admin 접속
2. 후보자 3명 등록 (홍길동/김철수/이영희, 사진 포함)
3. 홈 화면에서 3명 카드 표시 확인 (READY 상태)
4. 관리자 패널에서 선거 시작
5. 홈 화면 자동으로 ACTIVE 전환 확인
6. 지갑 A로 홍길동 투표 → 득표 수 1 갱신 확인
7. 지갑 B로 김철수 투표 → 득표 수 1 갱신 확인
8. 지갑 A로 재투표 시도 → "이미 투표하셨습니다" 오류 확인
9. 관리자 패널에서 선거 종료
10. 홈 화면 ENDED 전환, 동점(각 1표) → "공동 당선자" 표시 확인
11. Etherscan 링크 클릭 → 컨트랙트 주소 페이지 오픈 확인
```
